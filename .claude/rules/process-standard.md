# 过程文档金标准

> **本规则是项目生存的底线。** 任何开发者在任何时候加入项目，仅凭本文档体系索引的内容，就能在 30 分钟内理解项目全貌并开始开发。

---

## 一、为什么需要过程文档

1. **人员流动**：开发者可能随时离开，后来者必须能无缝接手
2. **AI 协作**：Claude Code 每次启动都读取 CLAUDE.md，文档即上下文
3. **决策追溯**：每个技术决策都应有记录，避免反复踩坑
4. **质量保证**：有文档的代码才是可维护的代码

---

## 二、文档体系结构

```
.claude/CLAUDE.md                          # 入口：项目概况 + 文档索引
.claude/rules/                             # 开发规范
├── code-style.md                          # 代码风格
├── cloud-functions.md                     # 云函数规范（含全部函数清单）
├── security.md                            # 安全规则
├── testing.md                             # 测试策略
└── process-standard.md                    # 本文件：过程金标准

docs/                                      # 项目文档
├── prd.md                                 # 产品需求（含实现状态标注）
├── database-schema.md                     # 数据库设计（实际 + 目标）
├── architecture-issues.md                 # 已知问题清单（含解决状态）
├── improvement-plan.md                    # 改进方案
├── implementation-*.md                    # 每次功能实施的详细记录
└── handover-YYYY-MM-DD.md                 # 每次开发会话的交接报告
```

## 三、必读规则

### 3.1 每次开发会话必须产生交接报告

文件名格式：`docs/handover-YYYY-MM-DD.md`

必须包含以下章节：

```markdown
# 交接报告 — YYYY-MM-DD 开发会话

## 基本信息
- 分支名称
- 基于（哪个分支/commit）
- 提交列表

## 完成内容
- 每个任务：做了什么、涉及哪些文件、关键决策

## 当前项目状态
- 功能状态表（功能 | 状态 | 说明）
- 已知未完成的功能

## 部署操作指南
- 首次部署步骤
- 需要手动操作的步骤

## 下一步建议
- 按优先级排序的待办事项
```

### 3.2 每次功能实施必须产生实施文档

文件名格式：`docs/implementation-{feature-name}.md`

必须包含：

```markdown
# {功能名称} — 实施文档

> 日期、参与者、基于分支

## 背景问题
- 为什么要做这个改动

## 设计决策记录
- D1: 决策内容 → 影响范围
- D2: ...

## 实施内容
- 任务拆分（每个任务：涉及文件、改动要点）

## 注意事项
- 遗留问题、待验证项
```

### 3.3 所有文档必须标注版本和更新日期

每个文档末尾必须包含：

```markdown
---
**文档版本**：v{N}
**最后更新**：YYYY-MM-DD
**变更说明**：简要说明本次更新了什么
```

### 3.4 CLAUDE.md 必须保持最新

CLAUDE.md 是整个文档体系的入口。以下变更发生时必须同步更新：

- 新增/删除云函数
- 新增/删除页面
- 新增/删除数据库集合
- 修改了核心约束或技术栈
- 发现了新的已知问题
- 完成了之前未完成的功能

## 四、文档质量标准

### 4.1 不删除原则

- **尽量不删除文档内容**，而是标记为"已过时"或"已实现"
- 过时的内容用 `~~删除线~~` 或 `> [已过时]` 标注
- 这样新人可以看到项目演进的历史

### 4.2 实事求是原则

- 文档中的状态标注必须反映代码的**实际状态**
- "已实现"必须是代码中真实存在的功能
- "未实现"必须注明是完全没有代码还是有部分代码
- 禁止使用模糊描述如"基本完成"、"差不多"

### 4.3 可操作原则

- 部署指南必须是可以逐步执行的
- 问题描述必须包含文件路径和行号
- 建议方案必须具体到涉及哪些文件、改什么

### 4.4 索引一致原则

- CLAUDE.md 中的文件列表必须与实际文件一致
- 云函数数量必须与 `cloudfunctions/` 目录中的实际数量一致
- 页面数量必须与 `app.json` 中注册的数量一致
- 集合数量必须与代码中实际使用的数量一致

## 五、新人上手检查清单

新加入项目的开发者应按以下顺序阅读：

1. [ ] 阅读 `.claude/CLAUDE.md`（5 分钟）— 项目全貌
2. [ ] 阅读 `.claude/rules/process-standard.md`（本文件，3 分钟）— 过程规范
3. [ ] 阅读最新的 `docs/handover-*.md`（5 分钟）— 最近变更
4. [ ] 浏览 `docs/architecture-issues.md`（5 分钟）— 已知问题
5. [ ] 阅读 `.claude/rules/cloud-functions.md`（5 分钟）— 云函数清单
6. [ ] 执行部署操作指南（5 分钟）— 跑起来
7. [ ] 开始开发

## 六、变更记录模板

每次重大变更应在 CLAUDE.md 或相关文档中留下记录：

```
### YYYY-MM-DD 变更记录
- 新增：{新增了什么}
- 修改：{修改了什么，从什么改为什么}
- 修复：{修复了什么问题}
- 删除：{删除了什么，原因}
```
