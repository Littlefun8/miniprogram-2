# 毕业论文写作规范与设计标准

## 1. 学术措辞统一规范

本文档规定全文统一采用的学术措辞标准，确保论文语体风格一致、提高学术规范性。

### 1.1 架构层次命名规范（按语境灵活使用）

#### 三个核心术语的准确使用指南

| 术语 | 适用语境 | 对应词 | 适用章节 | 示例 |
|---|---|---|---|---|
| **表现层** | 讨论架构、分层、设计模式 | 逻辑层、数据层 | 第3章（系统设计） | "三层架构中，表现层负责视图渲染，逻辑层负责业务校验" |
| **客户端** | 讨论网络请求、时序图交互 | 服务端、服务器 | 第3章（交互设计）、第4章（接口设计）| "客户端发起 wx.login 请求，服务端校验 Token 有效性" |
| **前端** | 讨论技术栈、代码实现、UI 组件 | 后端 | 第1、2、5 章 | "系统前端采用微信原生语法（WXML）开发" |

#### 禁止全局替换规则
**严禁盲目全局替换**。应根据上表灵活选择术语，确保学术专业性与自然表达的平衡。

### 1.2 异常处理与用户反馈规范

| 原始表达 | 学术表达 | 场景 |
|---------|---------|------|
| 给出失败提示 | 触发异常处理逻辑并提示用户 | 验证失败、权限拒绝 |
| 直接加载入口 | 依据角色权限动态渲染业务视图 | 登录成功后进入功能页面 |
| 显示失败提示 | 系统触发异常处理逻辑并提示用户重试 | 网络异常、查询失败 |
| 前端开发 | 表现层实现 | 技术实现章节 |

### 1.3 数据操作术语规范

| 操作类型 | 推荐表达 | 示例 |
|---------|---------|------|
| 数据查询 | 查询、调用查询接口 | "服务端按 OPENID 构造查询条件后返回" |
| 数据写入 | 写入、生成记录、持久化 | "系统写入申请记录、快照和时间线" |
| 数据更新 | 更新状态、流转 | "系统按状态机规则更新职位状态" |
| 数据校验 | 校验、执行验证逻辑 | "服务端先校验参数完整性" |

### 1.4 系统行为表达规范

| 原始表达 | 学术表达 | 适用场景 |
|---------|---------|---------|
| 页面显示XX | 系统渲染XX、表现层展示XX | 前端页面呈现 |
| 返回错误 | 返回异常分支、返回权限拒绝 | 业务判断失败 |
| 进入流程 | 触发流程、进入业务环节 | 业务流程转移 |
| 调用函数 | 调用XX云函数、触发XX接口 | 服务端交互 |

## 2. 时序图描述规范

### 2.1 时序图描述的四步公式

每个时序图下方的描述文字应包含以下四个要素：

1. **链路参与者**：明确涉及的端、云函数、数据集合
   - 示例："主要涉及微信客户端、`login` 云函数、`setUserRole` 云函数和用户数据集合"

2. **触发与请求**：业务动作触发时传递的关键参数（不写代码，写业务字段）
   - 示例："客户端先发起登录请求，服务端根据 OPENID 查询用户信息"

3. **核心处理与分支**（最重要）：服务端做了什么判断，如果失败走哪个分支，如果成功走哪个分支
   - 示例："若存在重复记录则返回拦截结果；若不存在则写入申请记录"

4. **持久化与返回**：数据写到了哪里，客户端收到结果后发生什么变化
   - 示例："并返回提交成功状态"、"页面依此渲染状态和时间线"

### 2.2 时序图描述的反面教材与改进

#### 反面教材（过于简短）
```
登录与角色确认场景中，页面先调用登录云函数获取用户信息；
当用户未设置角色时，再调用角色设置云函数写入角色字段，页面据此加载对应功能入口。
```

#### 改进版本（按四步公式）
```
登录与角色确认场景主要涉及微信客户端、`login` 云函数、`setUserRole` 云函数和用户数据集合。
用户进入系统后，客户端先发起登录请求，服务端根据 OPENID 查询用户信息并返回当前角色状态。

当返回结果中未包含角色信息时，客户端进入角色选择流程，携带 `userType` 参数调用 `setUserRole` 写入角色字段；
当角色已存在时，客户端依据角色权限动态渲染业务视图。
若登录请求异常或角色写入失败，系统触发异常处理逻辑并提示用户，同时保留重新触发入口。
```

## 3. 模块设计规范

### 3.1 模块组织的层次结构

每个模块设计应遵循以下组织方式：

```
### X.X.X 模块名称设计

[第一段] 模块组成说明
该模块由 A、B、C 三部分组成。**表现层** 负责 XX；**逻辑层** 负责 YY；**数据层** 负责 ZZ。

[第二段] 设计原则说明
在该模块的设计中，[阐述设计考量与权衡]。此部分的逻辑层服务主要由 `xxx` 云函数与 `yyy` 云函数提供支撑。

[如有必要] 技术特性说明
在系统设计中，[阐述业务流转特性]。该模块的核心业务由 `xxx`、`yyy`、`zzz` 等云函数协同完成。
```

### 3.2 模块命名与功能对应关系

确保以下四个模块在全文保持一致：

1. **用户与权限管理模块** → `login`, `setUserRole`
2. **职位管理模块** → `postJob`, `auditJob`, `getJobList`, `getJobDetail`
3. **申请与进度管理模块** → `applyJob`, `updateApplicationStatus`, `getApplications`
4. **通知与统计模块** → `getNotifications`, `getTeacherStats`

## 5. 内容检查清单

完成论文稿件前应检查以下项：

- [ ] 术语按语境灵活使用：第1、2、5章使用"前端/后端"；第3章系统设计用"表现层/逻辑层/数据层"；第3章交互设计用"客户端/服务端"
- [ ] 异常处理表达统一为"触发异常处理逻辑并提示用户"或"系统触发异常处理逻辑"
- [ ] 每个时序图下方包含参与者、请求、分支、返回四个要素
- [ ] 模块名称与云函数对应关系在第2、3、4章保持一致
- [ ] 所有用例描述表格式一致（纵向单行表）
- [ ] 图表编号与正文引用一致
- [ ] 没有出现过度设计或技术术语堆砌
- [ ] 语体避免AI感（不使用"在XX的基础上"、"XX有助于"等套路表达）
