# 中文摘要

本文围绕高校就业内推场景，设计并实现了一套基于微信小程序与腾讯云开发的“酱菜内推系统”。系统面向学生、校友与教师三类角色，构建了从职位发布、教师审核、学生申请到校友处理申请的协同闭环。为满足校园内推业务中对真实性、可追踪性与安全性的要求，系统在服务端引入 OPENID 身份识别、角色权限校验、申请状态机和敏感字段门控等机制，确保关键业务逻辑集中在云函数层执行。

在功能实现上，系统完成了职位列表检索、职位详情展示、职位发布审核、申请提交与进度追踪、通知反馈及教师统计等核心模块。其中，申请记录采用状态流转机制管理，职位详情仅在申请通过后返回内推码、联系方式和职位链接等敏感信息；职位发布与申请处理过程则通过云函数白名单写入与权限校验保证数据安全。系统采用模块化设计思想，将前端页面与云函数逻辑分层组织，提升了系统的可维护性与扩展性。

实践结果表明，该系统能够较好地满足校园内推业务的协同管理需求，为校友资源与学生求职需求的对接提供了稳定、轻量且易部署的工程实现方案，也为后续扩展图表可视化、身份认证增强和推荐分析功能奠定了基础。

# English Title

Design and Implementation of the Jiangcai Referral System Based on WeChat Mini Program

# Abstract

This thesis presents the design and implementation of the Jiangcai Referral System, a WeChat Mini Program-based referral platform built on Tencent Cloud Development. The system targets three core roles in a campus referral scenario: students, alumni, and teachers. It provides an end-to-end workflow that covers job posting, teacher review, student application, and alumni-side application processing.

To ensure reliability and security in the referral process, the system adopts server-side identity recognition based on OPENID, role-based permission checks, application state transitions, and sensitive field access control. Key business logic is implemented in cloud functions rather than on the client side, which improves maintainability and reduces the risk of unauthorized access. The overall architecture follows a layered design pattern, separating page presentation, cloud function services, and database persistence.

The implemented system includes core modules such as job listing, job detail display, job posting and review, application submission and tracking, notification delivery, and teacher-side statistics. The results show that the system can effectively support a lightweight and practical campus referral workflow, and it also lays a foundation for future extensions such as enhanced visualization, stronger identity verification, and recommendation analysis.

WeChat Mini Program; Tencent Cloud Development; campus referral; state machine; permission control; cloud functions

# 第1章 绪论

## 1.1 研究背景与意义
随着数字化校园建设的持续推进，学生就业服务正从传统线下咨询和分散信息发布逐步转向线上协同平台。对于高校求职场景而言，学生、校友与教师三方之间存在明显的信息不对称问题：学生难以及时获得高质量岗位信息，校友缺乏低门槛的校内岗位发布入口，教师在审核与管理环节中需要承担较高的沟通成本。基于微信生态构建轻量级就业协同系统，能够在不增加用户使用门槛的前提下，提升信息流转效率和管理规范性。

本课题围绕“酱菜内推系统”的设计与实现展开，目标是在微信小程序环境中构建一个可落地的内推闭环平台。系统以“校友发布职位、教师审核背书、学生申请、校友处理申请”为核心主链路，并在关键环节引入权限控制与状态机约束，兼顾业务可用性与数据安全性。该研究具有以下实践价值：

1. 为校园就业内推场景提供轻量、低运维成本的工程化方案；
2. 通过角色分工与流程标准化，降低人工协调成本；
3. 为后续扩展推荐算法、数据分析看板等功能提供可复用的系统基础。

## 1.2 同类系统与现状简述
当前常见招聘平台多面向社会化求职，难以直接承载“校友资源反哺 + 教师审核背书”的校内场景。部分高校就业系统虽覆盖信息发布，但在移动端交互体验、角色协同效率和过程可追踪性方面仍存在不足。与通用平台相比，本系统在场景定位上更垂直：一方面强调校友资源与学生求职需求的对接；另一方面通过教师审核机制提升岗位可信度，减少无效信息传播。

在技术实现层面，本系统采用微信小程序原生方案与腾讯云开发服务，避免自建服务器的高运维负担；在业务实现层面，系统通过云函数集中处理关键权限逻辑，使前后端职责边界更加清晰。这种设计路径适合本科毕业设计在有限周期内完成“可运行系统 + 可解释工程方案”的双重目标。

## 1.3 研究目标与主要工作
本文以软件工程方法为指导，围绕需求分析、系统设计、数据库设计与实现落地四个层面开展工作。主要目标如下：

- 完成三角色协同业务流程建模，明确系统功能边界；
- 构建前后端分层架构，定义页面层与云函数层职责；
- 设计与实现可扩展的数据模型和关键状态流转规则；
- 在实际项目中落地关键功能，包括职位发布审核、申请处理、敏感信息控制等。

为达成上述目标，本文完成的主要工作包括：

# 第2章 需求分析

## 2.1 业务场景与角色分析
“酱菜内推系统”面向高校就业内推场景。与普通招聘平台相比，本系统除职位发布与申请外，还包含教师审核、校友处理申请、敏感信息分级展示等业务约束。因此，本章从角色协同、权限边界和业务流程三个方面开展需求分析。

系统参与者包括学生、校友和教师三类角色。学生关注岗位检索效率和申请进度可见性；校友关注职位发布效率和申请处理效率；教师关注职位审核质量和运行数据统计。三类角色共同构成完整业务过程，并要求系统在服务端完成身份与权限判定。

## 2.2 功能性需求分析
为保证需求可核验，本章采用“需求编号、用例编号、功能描述”三项对应方式。需求编号统一为 `REQ-F-*`，用例编号统一为 `UC-*`。系统总用例关系见图2-1，主要活动流程见图2-2至图2-5，模块分解见表2-2。

### 2.2.1 用户与权限管理模块（REQ-F-01）
用户与权限管理模块用于完成身份初始化、角色确认和会话恢复。该模块是系统运行的入口模块，其需求既关系角色识别准确性，也关系后续业务权限控制有效性。其主要需求如下：

（1）自动注册与登录（REQ-F-01-01）；

（2）首次角色设置（REQ-F-01-02）；

（3）静默登录与本地状态同步（REQ-F-01-03、REQ-F-01-04）。

本模块对应的实现内容在后续系统实现章节中展开。

### 2.2.2 职位管理模块（REQ-F-02、REQ-F-04）
职位管理模块覆盖职位发布、职位审核、职位列表展示和职位详情展示。该模块直接决定学生端岗位信息质量与可见范围。其主要需求如下：

（1）校友发布职位并进入待审核状态（REQ-F-02-01）；

（2）教师完成职位审核并返回结果（REQ-F-02-02）；

（3）学生端按发布状态查看职位（REQ-F-02-03）；

（4）职位详情按业务状态分级返回展示信息（REQ-F-04-01、REQ-F-04-02、REQ-F-04-03）。

发布审核流程见图2-2，详情与分级展示流程见图2-5。

### 2.2.3 申请与进度管理模块（REQ-F-03）
申请与进度管理模块覆盖申请提交、申请处理和进度查看。该模块是学生与校友协同最集中的业务区域，需求重点在过程可追踪和结果可反馈。其主要需求如下：

（1）学生提交申请（REQ-F-03-01）；

（2）系统拦截重复申请并固化申请快照（REQ-F-03-02、REQ-F-03-03）；

（3）校友处理申请并回写结果（REQ-F-03-04）；

（4）学生与校友按角色视角查询申请进度（REQ-F-03-05）。

申请相关流程见图2-3、图2-4。

### 2.2.4 通知与统计模块（REQ-F-05）
通知与统计模块用于承载结果通知和教师统计。该模块属于运行支撑模块，为多角色提供消息反馈和运行观察能力。其主要需求如下：

（1）系统在关键业务节点生成通知并支持分页查询（REQ-F-05-03）；

（2）教师端提供统计聚合查询能力并限制访问角色（REQ-F-05-01、REQ-F-05-02）。

本模块相关实现在第4章系统实现中给出。

## 2.3 非功能需求分析

### 2.3.1 安全性需求
系统涉及职位审核、申请状态流转和敏感字段展示等关键场景，因此安全性需求尤为重要。首先，身份识别必须基于云开发上下文中的 OPENID，而不能依赖前端上传的用户标识；其次，所有涉及权限边界的操作必须在云函数内部完成角色判断，避免前端绕过；最后，内推码、联系微信、职位链接等敏感信息应在服务端按业务状态进行控制，确保只有符合条件的申请人可见。

### 2.3.2 性能需求
系统定位于校园场景，数据规模相对有限，但仍需保证列表查询和统计查询具有稳定响应。职位列表、申请列表与通知列表应采用分页加载策略，并限制单页最大返回数量，以避免一次性返回过多数据影响体验。统计模块虽然属于聚合查询，但在当前业务规模下仍应保证用户在可接受时间内完成加载。

### 2.3.3 可维护性与扩展性需求
为了适应后续迭代，系统需要在结构上保持清晰的模块边界。前端采用页面组织方式，后端采用“一类业务对应一个云函数”的方式，有利于独立开发与部署。数据字段与状态值采用统一命名规范，可减少前后端联调中的语义偏差。此外，系统保留了图表增强、身份认证完善与推荐能力扩展等后续发展空间。

## 2.4 用例分析与规约
本系统将关键用例写为结构化规约，规约内容包括用例编号、参与者、前置条件、基本事件流和异常处理。详细规约见表2-3，核心用例如下：

（1）`UC-S01` 浏览职位；

（2）`UC-S02` 申请职位；

（3）`UC-A01` 发布职位；

（4）`UC-A02` 处理申请；

（5）`UC-T01` 审核职位；

（6）`UC-T02` 查看统计。

上述用例既用于论文说明，也可作为测试与验收的输入。

## 2.5 需求可追踪矩阵
为保证可复现性，本章建立“需求ID到页面、云函数、关键校验和输出”的追踪关系，详见表2-5。该矩阵用于说明需求项与系统功能项之间的对应关系。

## 2.6 现状问题与敏捷改进建议
在需求与实现对照过程中，系统仍有改进空间。为便于后续迭代，本节给出当前阶段的重点优化事项，详细清单见 `10-ENGINEERING-IMPROVEMENTS.md`。本轮建议优先处理以下事项：

（1）申请状态更新时补齐时间线追加逻辑；

（2）统一云函数环境配置策略，降低多环境部署风险；

（3）将通知已读操作统一收敛到云函数入口。

## 2.7 本章小结
本章完成了系统需求分析，明确了业务角色、功能模块、关键用例和可追踪关系。上述内容为第3章系统设计和第4章系统实现提供了直接输入。

# 第3章 系统设计

## 3.1 设计说明
本章根据第2章需求分析结果，说明系统的总体结构、功能模块和主要业务流程。为保证章节分工清晰，本章重点回答“系统如何设计”，实现细节放在下一章展开。

## 3.2 总体架构设计
本系统采用三层结构，包括前端层、业务服务层和数据存储层。系统总体架构见图3-1。

### 3.2.1 前端层
前端层为微信小程序端，负责页面展示和用户交互。其主要组成如下：

（1）视图部分采用 WXML 与 WXSS，用于页面布局和样式展示；

（2）逻辑部分采用 JavaScript，通过页面对象管理生命周期与交互事件；

（3）工具部分封装通用方法，包括请求调用、本地缓存和权限检查。

### 3.2.2 业务服务层
业务服务层由腾讯云函数构成，负责处理业务规则和数据读写。系统采用“一类业务对应一个云函数”的组织方式。该层主要工作如下：

（1）接收页面请求并进行参数校验；

（2）执行角色判定和业务处理；

（3）返回统一格式的处理结果。

### 3.2.3 数据存储层
数据存储层采用云数据库，负责保存用户、职位、申请和通知等数据。其主要作用如下：

（1）保存各业务对象的基础数据；

（2）支撑列表查询、详情查询和统计查询；

（3）为后续功能扩展提供数据基础。

说明：本系统当前版本不包含独立 PC 端，也不采用 Spring Cloud 微服务网关结构，整体实现以微信小程序和云函数架构为主。

## 3.3 功能模块设计
按照业务目标和职责边界，系统划分为四个核心模块，模块关系见图3-2。

### 3.3.1 用户与权限管理模块
该模块用于完成登录、角色设置、会话恢复和权限判定，是各业务功能的统一入口。其核心任务包括：

（1）识别当前用户身份；

（2）确定用户角色；

（3）为后续业务操作提供权限依据。

### 3.3.2 职位管理模块
该模块覆盖职位发布、职位审核、职位列表查询和职位详情展示，属于同一业务对象（职位）的完整管理模块。其核心任务包括：

（1）校友提交职位信息；

（2）教师审核职位信息；

（3）学生按条件浏览已发布职位。

### 3.3.3 申请与进度管理模块
该模块覆盖学生申请、校友处理、学生进度查看和结果展示，属于同一业务对象（申请）的完整处理模块。其核心任务包括：

（1）学生提交职位申请；

（2）校友处理申请结果；

（3）学生查看申请进度与处理结果。

### 3.3.4 通知与统计模块
该模块包含结果通知和统计分析两类支撑功能，服务于系统运行反馈和教师管理视角。其核心任务包括：

（1）向相关用户发送审核与申请结果通知；

（2）汇总职位与申请数据，为教师提供统计页面数据。

## 3.4 核心业务流程设计

### 3.4.1 职位发布与审核流程
校友在职位管理模块提交职位后，系统将其置为待审核状态。教师在同一模块完成审核后，职位进入发布状态或驳回状态。流程图见图3-3。

### 3.4.2 职位申请与处理流程
学生在申请与进度管理模块提交申请，校友在该模块处理申请。处理结果随后反馈给学生。流程图见图3-4。

### 3.4.3 敏感信息展示流程
职位详情中的内推码和联系方式采用分级展示方式。该流程由职位管理模块与申请与进度管理模块共同支撑，学生在不同申请结果下看到的信息不同。流程图见图3-5。

## 3.5 页面与服务协同设计
页面层与服务层通过云函数调用完成协同。主要接口包括职位列表查询、职位发布、职位申请、申请处理、职位详情查询和教师统计查询。协同关系见图3-6。

﻿# 第4章 系统实现

## 4.1 实现说明
本章按照第3章的模块顺序，说明系统的实现方式。每个模块均从页面入口、云函数处理和结果反馈三个方面展开，保证章节结构与设计章节一致。

## 4.2 用户与权限管理模块实现
该模块对应登录、角色设置和会话恢复功能。相关实现由小程序登录流程与 `login`、`setUserRole` 云函数共同完成。其实现过程如下：

（1）用户进入系统后，前端先检查本地会话状态，并发起静默登录；

（2）云函数根据用户身份信息查询或创建用户档案；

（3）首次使用时由用户选择角色，系统写入角色信息并同步到本地缓存。

该模块完成后，系统可为后续业务模块提供统一身份和权限依据。模块实现示意见图4-1。

## 4.3 职位管理模块实现
该模块包含职位发布、职位审核、职位列表和职位详情四类实现内容，涉及校友、教师、学生三个角色。

（1）在发布环节，校友通过发布页面提交职位信息，`postJob` 云函数完成数据写入；

（2）在审核环节，教师通过审核页面处理待审核职位，`auditJob` 云函数写回审核结果；

（3）在查询环节，学生通过职位列表与详情页面访问岗位信息，列表与详情分别调用 `getJobList` 和 `getJobDetail` 云函数。

该模块实现后，系统能够完成职位从提交到展示的完整过程。模块实现示意见图4-2。

## 4.4 申请与进度管理模块实现
该模块包含申请提交、申请处理和进度查看三类实现内容，重点覆盖学生与校友的协同操作。

（1）学生在职位详情页面提交申请，系统调用 `applyJob` 云函数创建申请记录；

（2）校友在申请管理页面处理申请，系统调用 `updateApplicationStatus` 云函数更新处理结果；

（3）学生在个人页面查看申请进度，系统根据当前处理结果返回对应状态信息。

该模块实现后，申请过程的提交、处理和反馈能够在页面中连续呈现。模块实现示意见图4-3。

## 4.5 通知与统计模块实现
该模块包含结果通知和统计展示两类支撑功能。

（1）在通知方面，系统在审核完成和申请处理完成后生成通知记录，用户在通知页面查看消息；

（2）在统计方面，教师通过统计页面调用 `getTeacherStats` 云函数，查看职位与申请相关数据。

该模块实现后，系统可以提供基础运行反馈和管理视图。模块实现示意见图4-4。

## 4.6 部署与联调实现
系统部署采用前端构建与云函数逐项部署方式。联调时按“用户登录、职位发布、职位审核、职位申请、申请处理、结果查看”的顺序进行，确保核心业务在多角色场景下可连续运行。
