# 中文摘要

本文围绕高校就业内推场景，设计并实现了一套基于微信小程序与腾讯云开发的“酱菜内推系统”。系统面向学生、校友与教师三类角色，构建了从职位发布、教师审核、学生申请到校友处理申请的协同闭环。为满足校园内推业务中对真实性、可追踪性与安全性的要求，系统在服务端引入 OPENID 身份识别、角色权限校验、申请状态机和敏感字段门控等机制，确保关键业务逻辑集中在云函数层执行。

在功能实现上，系统完成了职位列表检索、职位详情展示、职位发布审核、申请提交与进度追踪、通知反馈及教师统计等核心模块。其中，申请记录采用状态流转机制管理，职位详情仅在申请通过后返回内推码、联系方式和职位链接等敏感信息；职位发布与申请处理过程则通过云函数白名单写入与权限校验保证数据安全。系统采用模块化设计思想，将前端页面与云函数逻辑分层组织，提升了系统的可维护性与扩展性。

实践结果表明，该系统能够较好地满足校园内推业务的协同管理需求，为校友资源与学生求职需求的对接提供了稳定、轻量且易部署的工程实现方案，也为后续扩展图表可视化、身份认证增强和推荐分析功能奠定了基础。

## 关键词
微信小程序；腾讯云开发；校园内推；状态机；权限控制；云函数

# English Title

Design and Implementation of the Jiangcai Referral System Based on WeChat Mini Program

# Abstract

This thesis presents the design and implementation of the Jiangcai Referral System, a WeChat Mini Program-based referral platform built on Tencent Cloud Development. The system targets three core roles in a campus referral scenario: students, alumni, and teachers. It provides an end-to-end workflow that covers job posting, teacher review, student application, and alumni-side application processing.

To ensure reliability and security in the referral process, the system adopts server-side identity recognition based on OPENID, role-based permission checks, application state transitions, and sensitive field access control. Key business logic is implemented in cloud functions rather than on the client side, which improves maintainability and reduces the risk of unauthorized access. The overall architecture follows a layered design pattern, separating page presentation, cloud function services, and database persistence.

The implemented system includes core modules such as job listing, job detail display, job posting and review, application submission and tracking, notification delivery, and teacher-side statistics. The results show that the system can effectively support a lightweight and practical campus referral workflow, and it also lays a foundation for future extensions such as enhanced visualization, stronger identity verification, and recommendation analysis.

WeChat Mini Program; Tencent Cloud Development; campus referral; state machine; permission control; cloud functions

# 第1章 绪论

## 1.1 研究背景与意义
随着数字化校园建设的持续推进，学生就业服务正从传统线下咨询和分散信息发布逐步转向线上协同平台。对于高校求职场景而言，学生、校友与教师三方之间存在明显的信息不对称问题：学生难以及时获得高质量岗位信息，校友缺乏低门槛的校内岗位发布入口，教师在审核与管理环节中需要承担较高的沟通成本。基于微信生态构建轻量级就业协同系统，能够在不增加用户使用门槛的前提下，提升信息流转效率和管理规范性。

本课题围绕“酱菜内推系统”的设计与实现展开，目标是在微信小程序环境中构建一个可落地的内推闭环平台。系统以“校友发布职位、教师审核背书、学生申请、校友处理申请”为核心主链路，并在关键环节引入权限控制与状态机约束，兼顾业务可用性与数据安全性。该研究具有以下实践价值：

1. 为校园就业内推场景提供轻量、低运维成本的工程化方案；
2. 通过角色分工与流程标准化，降低人工协调成本；
3. 为后续扩展推荐算法、数据分析看板等功能提供可复用的系统基础。

## 1.2 同类系统与现状简述
当前常见招聘平台多面向社会化求职，难以直接承载“校友资源反哺 + 教师审核背书”的校内场景。部分高校就业系统虽覆盖信息发布，但在移动端交互体验、角色协同效率和过程可追踪性方面仍存在不足。与通用平台相比，本系统在场景定位上更垂直：一方面强调校友资源与学生求职需求的对接；另一方面通过教师审核机制提升岗位可信度，减少无效信息传播。

在技术实现层面，本系统采用微信小程序原生方案与腾讯云开发服务，避免自建服务器的高运维负担；在业务实现层面，系统通过云函数集中处理关键权限逻辑，使前后端职责边界更加清晰。这种设计路径适合本科毕业设计在有限周期内完成“可运行系统 + 可解释工程方案”的双重目标。

## 1.3 研究目标与主要工作
本文以软件工程方法为指导，围绕需求分析、系统设计、数据库设计与实现落地四个层面开展工作。主要目标如下：

- 完成三角色协同业务流程建模，明确系统功能边界；
- 构建前后端分层架构，定义页面层与云函数层职责；
- 设计与实现可扩展的数据模型和关键状态流转规则；
- 在实际项目中落地关键功能，包括职位发布审核、申请处理、敏感信息控制等。

为达成上述目标，本文完成的主要工作包括：

1. 梳理学生、校友、教师三类角色的核心需求，形成功能需求与非功能需求集合；
2. 设计系统总体架构与模块划分，明确云函数调用链与数据流；

# 第2章 需求分析

## 2.1 业务场景与角色分析
“酱菜内推系统”面向的是高校就业内推这一典型协同场景。与普通招聘平台相比，该场景不仅涉及职位发布与求职申请，还额外包含教师背书审核、校友处理申请以及敏感信息分级展示等业务约束。因此，系统的需求分析不能只停留在“信息发布平台”的层面，而应从角色协同、权限边界和流程闭环三个维度进行定义。

系统的核心参与者包括学生、校友、教师三类角色。学生是内推申请的主体，关注的是岗位获取效率、申请流程便利性以及申请进度可追踪性；校友是岗位信息的发布者与申请处理者，关注的是职位录入效率、申请管理效率以及对候选人的快速反馈能力；教师是职位背书审核者与统计观察者，关注的是岗位真实性、审核可控性以及整体运行态势。三类角色共同构成了系统的业务闭环，同时也决定了系统必须采用服务端权限控制和状态管理机制。

## 2.2 功能需求分析
从业务链路看，系统功能需求可以划分为身份管理、职位管理、申请管理、通知管理和统计管理五个层次。

### 2.2.1 身份管理需求
系统应支持用户首次访问时的自动注册与身份绑定，使用户无需额外安装应用即可进入平台。用户首次选择角色后，系统应保留该角色信息并作为后续权限判断的依据。为降低使用门槛，系统提供静默登录与交互式登录两种方式：前者用于首次初始化与日常唤起，后者用于明确角色选择场景。

### 2.2.2 职位管理需求
校友应能够在小程序中发布职位信息，发布内容至少包括职位名称、薪资范围、工作地点、标签、职位描述、任职要求及内推相关说明。教师应能够对待审核职位执行通过或拒绝操作，并在审核结果中体现原因或审核信息。学生端仅允许查看已通过审核且处于可展示状态的职位，从而保证岗位信息的公开范围与审核结果一致。

### 2.2.3 申请管理需求
学生在浏览职位后可发起申请，系统需要对重复投递进行控制，并在申请时固化简历快照，以保证申请当时的个人信息不会因后续修改而失真。校友端应支持按申请状态查看与处理申请记录，并能够对申请结果进行分阶段更新，从而使申请流程具有可追踪性。

### 2.2.4 通知与统计需求
当职位审核结果或申请状态发生变化时，系统应能够通知相关用户，以减少跨角色沟通成本。教师端应能够查看平台运行统计，包括申请总量、状态分布、热门岗位、活跃校友以及高成功率学生等信息，为教学指导与就业分析提供数据支持。

## 2.3 非功能需求分析

### 2.3.1 安全性需求
系统涉及职位审核、申请状态流转和敏感字段展示等关键场景，因此安全性需求尤为重要。首先，身份识别必须基于云开发上下文中的 OPENID，而不能依赖前端上传的用户标识；其次，所有涉及权限边界的操作必须在云函数内部完成角色判断，避免前端绕过；最后，内推码、联系微信、职位链接等敏感信息应在服务端按业务状态进行控制，确保只有符合条件的申请人可见。

### 2.3.2 性能需求
系统定位于校园场景，数据规模相对有限，但仍需保证列表查询和统计查询具有稳定响应。职位列表、申请列表与通知列表应采用分页加载策略，并限制单页最大返回数量，以避免一次性返回过多数据影响体验。统计模块虽然属于聚合查询，但在当前业务规模下仍应保证用户在可接受时间内完成加载。

### 2.3.3 可维护性与扩展性需求
为了适应后续迭代，系统需要在结构上保持清晰的模块边界。前端采用页面组织方式，后端采用“一类业务对应一个云函数”的方式，有利于独立开发与部署。数据字段与状态值采用统一命名规范，可减少前后端联调中的语义偏差。此外，系统保留了图表增强、身份认证完善与推荐能力扩展等后续发展空间。

## 2.4 用例分析
从用例视角看，学生的主要用例包括浏览职位、收藏职位、提交申请和查看申请进度；校友的主要用例包括发布职位、管理申请和通知反馈；教师的主要用例包括审核职位和查看统计。三类用例共同构成一条从职位发布到申请处理再到结果反馈的闭环链路。

在论文表达上，建议采用“总用例图 + 角色功能矩阵表”的组合方式：总用例图用于说明角色边界和系统边界，角色功能矩阵表用于补充功能细节和权限说明。这样既能满足论文的图形表达要求，又能提升可读性。

## 2.5 本章小结
本章从高校就业内推场景出发，分析了系统的核心角色、功能需求与非功能需求，并明确了系统的用例边界。需求分析结果表明，本系统不仅需要实现基础信息流转，还必须在身份、权限和状态流转层面形成完整约束，这为后续章节的系统设计提供了直接依据。

# 第3章 系统概要设计

## 3.1 总体架构设计
本系统采用微信小程序前端、腾讯云函数服务层和云数据库存储层组成的三层架构。前端负责页面渲染、用户交互与基础状态展示；云函数负责承载主要业务逻辑、权限控制与数据聚合；云数据库负责保存用户、职位、申请、通知等结构化业务数据。页面层通过 `wx.cloud.callFunction` 与后端交互，使客户端无需直接处理敏感规则，从而降低了前端逻辑复杂度。

从设计理念上看，该架构兼顾了毕业设计场景下的开发效率与工程规范性。一方面，云开发模式减少了服务器部署与环境运维成本；另一方面，服务端集中处理权限、状态与数据一致性问题，使系统更符合软件工程中“分层解耦、职责清晰”的设计原则。

## 3.2 功能模块划分
结合业务流程与页面结构，系统可划分为以下六个功能模块。

### 3.2.1 用户与身份模块
该模块负责登录、角色设置、个人信息同步与本地状态管理。其作用不是单纯完成账号进入，而是为后续权限控制提供可信身份基础。

### 3.2.2 职位管理模块
该模块覆盖职位发布、职位列表查询和职位详情展示，是系统最基础的业务入口。学生、校友和教师对职位信息的访问范围不同，因此该模块需要同时满足公开展示与权限隔离两类要求。

### 3.2.3 审核与背书模块
教师在该模块中对待审核职位进行真实性审核，审核结果决定岗位是否可在学生端展示。该设计使职位发布不再是单向写入，而是形成“提交-审核-发布”的双阶段流程。

### 3.2.4 申请处理模块
学生提交申请后进入状态流转过程，校友在该模块中进行处理。状态变化由云函数统一控制，前端仅负责显示与交互。

### 3.2.5 通知模块
通知模块用于承载审核结果、申请结果和状态变化提醒，使系统形成闭环反馈机制。

### 3.2.6 统计模块
统计模块面向教师提供数据概览、趋势分析和排行展示。它将分散的业务数据聚合为可读信息，帮助教师理解系统运行情况。

## 3.3 核心业务流程设计

### 3.3.1 职位发布与审核流程
系统在业务上将职位发布与职位生效拆分为两个阶段。校友发布职位后，职位状态初始化为 pending，表示该职位尚未经过教师审核。教师审核通过后，职位状态更新为 published，学生端即可检索；若审核不通过，则状态更新为 rejected，并保留拒审原因。该流程保证了岗位进入学生视野之前经过必要背书，从机制上提高了岗位可信度。

### 3.3.2 申请流转与处理流程
学生发起申请后，系统创建申请记录并将初始状态置为 pending。随后，校友根据实际情况将申请状态推进至 processing、accepted 或 rejected。流程设计上采用有限状态机模型，避免状态越级跳转或终态回退，确保申请过程具备可追踪性与一致性。

### 3.3.3 敏感信息解锁流程
职位详情中的内推码、联系微信和职位链接属于敏感字段。系统在详情云函数中先判断当前用户是否已对该职位申请且状态为 accepted，再决定是否返回这些字段。此设计将“信息解锁”与“申请结果”直接关联，使业务规则清晰且可验证。

## 3.4 前后端职责划分
系统在职责划分上遵循“前端负责展示、后端负责规则、数据库负责存储”的基本原则。前端主要负责页面渲染、参数收集和用户交互反馈；云函数负责身份识别、角色校验、状态更新和数据聚合；云数据库负责持久化保存各类业务对象。该分工能够避免将复杂业务逻辑散落在多个页面中，从而降低维护成本。

在实际实现中，涉及权限和状态变化的操作均由云函数承接，前端不直接写入核心业务数据。这种设计既符合小程序云开发的使用模式，也更符合企业级系统设计中对安全边界的要求。

## 3.5 本章小结
本章从体系结构、功能模块和核心流程三个层面完成了系统概要设计。通过明确模块边界与职责分工，系统形成了从用户身份到业务状态再到数据存储的完整链路，为下一章详细设计提供了明确的展开方向。

# 第4章 系统详细设计

## 4.1 鉴权与权限控制设计
系统的权限设计以微信云开发提供的 OPENID 为身份基础。与直接依赖前端传参相比，基于 `cloud.getWXContext().OPENID` 的身份识别方式能够保证调用者身份来源可靠，并避免用户通过篡改请求参数绕过权限检查。系统在关键云函数中均以 OPENID 作为查询用户档案与判断角色的唯一依据，再结合 `users.userType` 完成角色级校验。

从设计目标上看，鉴权模块并不仅仅是“判断能不能访问”，而是要完成身份注册、角色绑定、权限校验三项职责：用户首次登录时自动建立基础档案；首次角色选择后将角色信息持久化；后续业务调用时根据角色决定是否允许发布、审核或统计查询。该设计使系统形成“身份确定 + 角色确定 + 权限确定”的三层控制链路。

## 4.2 职位模块详细设计
职位模块是整个系统的业务入口，其详细设计围绕发布、审核、查询和详情四类操作展开。

### 4.2.1 职位发布设计
校友在前端提交职位表单后，云函数采用白名单方式构建职位对象，仅保留与业务相关的字段，例如标题、薪资、地点、描述、要求、标签和内推说明等。发布成功时，职位状态初始化为 pending，表示其尚未通过教师审核。通过白名单写入，系统可有效避免前端额外字段进入数据库，提升数据安全性和结构一致性。

### 4.2.2 职位审核设计
教师对 pending 状态的职位执行审核操作。若审核通过，则职位状态变更为 published，并写入审核教师信息；若审核不通过，则职位状态变更为 rejected，并保留拒审原因。该设计将审核结果与岗位生命周期直接关联，保证岗位从提交到可见的过程具有明确的状态依据。

### 4.2.3 职位查询与详情设计
职位列表接口默认只返回 published 职位，并支持分页、关键词和筛选条件。职位详情接口则在返回完整岗位信息的同时，根据当前用户申请状态判断是否展示敏感字段。列表与详情的分工使系统既能满足公开浏览，又能支持细粒度信息解锁。

## 4.3 申请与状态机模块设计
申请模块的设计目标是保证申请过程可追踪、可控制且不可重复。学生申请时，系统首先校验目标职位是否处于可申请状态，然后检查是否已经提交过该职位申请，若已存在则直接拒绝重复申请。通过该方式，系统避免同一用户对同一职位重复投递，减少数据冗余与后续处理成本。

申请记录中保存了申请人信息、职位快照、简历快照、时间线和可选背书数据。其中，简历快照用于保存申请当时的学生简历信息，保证历史记录不会因后续修改而失真；时间线则用于记录申请从提交到处理的关键节点，增强过程可追溯性。

系统的状态机设计如下：

- `pending`：申请刚提交，等待校友处理；
- `processing`：校友已查看或正在处理；
- `accepted`：申请通过，后续可解锁敏感信息；
- `rejected`：申请不通过，流程终止。

状态更新接口仅允许状态按上述路径推进，不允许从终态回退，也不允许跨阶段跳转。通过显式状态机约束，系统可以避免非法写入和业务绕过。

## 4.4 敏感字段控制设计
职位详情中的 `referralCode`、`contactWechat` 和 `jobLink` 属于仅在特定条件下可见的敏感字段。系统在详情云函数中先查询当前用户对该职位的申请状态，只有当状态为 accepted 时才返回这些字段，否则在服务端直接删除后返回。这种“服务端门控”比前端隐藏更可靠，因为前端隐藏仅影响展示，不影响数据传输。

该设计的目标不仅是保护敏感信息，更重要的是把“权益解锁”与“申请结果”建立强绑定关系。换言之，系统不是简单地展示岗位详情，而是把详情视为一种按条件分级开放的信息资源。

## 4.5 数据库与索引设计
系统采用云数据库保存业务数据，核心集合包括 `users`、`jobs`、`applications`、`notifications`、`favorites` 和 `userActions`。在字段设计上，系统统一采用 camelCase 命名，并使用字符串枚举表达状态值，从而保持前后端语义一致。

在索引设计上，系统重点围绕高频查询路径进行优化：职位列表按状态和时间排序；申请列表按用户与状态筛选；通知列表按用户与已读状态筛选。`createIndexes` 云函数用于批量创建索引，并作为运维入口留存，保证系统在部署后仍能按需补齐数据库索引。

从工程角度看，该数据库设计体现了“面向查询路径设计结构”的原则，即数据库结构并非只依据业务名词组织，还需要结合实际访问模式进行索引与冗余字段设计，以降低后续查询成本。

## 4.6 本章小结
本章从身份权限、职位模块、申请状态机、敏感字段控制以及数据库索引五个方面展开了系统详细设计。相关设计既确保了关键业务流程的正确性，也为后续系统实现提供了清晰的功能边界和数据边界。

# 第5章 系统实现

## 5.1 前端页面实现

### 5.1.1 职位列表页实现
职位列表页是学生进入系统后的主要入口，承担职位浏览、筛选和分页加载功能。页面在初始化时同步本地登录状态，并通过云函数拉取职位数据。用户在搜索框中输入关键词或切换城市、岗位类型、排序条件后，页面会重新组织查询参数并刷新列表，从而形成可交互的检索体验。该页面的实现重点不在于复杂动画，而在于保证岗位信息获取与展示的稳定性。

### 5.1.2 职位详情页实现
职位详情页采用状态驱动的界面组织方式。系统根据用户是否登录、是否已申请以及申请结果状态，分别展示未申请、待审核、已通过和已拒绝等不同界面内容。未申请状态下，页面引导用户完成申请；待审核状态下，页面向用户反馈流程正在处理；已通过状态下，页面展示已解锁的内推信息；已拒绝状态下，页面提示申请结果并保留继续浏览入口。该实现方式使页面逻辑与业务状态保持一致，降低了复杂条件判断带来的维护成本。

### 5.1.3 申请管理与教师统计页面实现
申请管理页面服务于校友对申请记录的处理，核心是状态切换与结果反馈。教师统计页面则面向教师侧的数据观察需求，通过调用聚合云函数获取统计数据，再在前端渲染概览、分布、排行和趋势模块。该设计体现了典型的“前端负责展示、后端负责统计”的分工方式，避免了在页面层编写过多数据计算逻辑。

## 5.2 云函数实现

### 5.2.1 登录与角色设置
登录云函数负责基于 OPENID 自动识别或创建用户记录，首次访问即可生成基础档案。角色设置云函数则用于完成首次角色绑定，并将角色状态写入数据库与本地缓存。通过这两个云函数，系统形成了轻量化的身份初始化流程。

### 5.2.2 职位发布与审核实现
职位发布云函数先完成参数校验，再检查调用者角色是否为校友或教师，随后使用白名单方式组装职位数据并写入数据库。教师审核云函数负责处理 approve/reject 两种动作：当审核通过时，更新职位状态并写入审核教师信息；当审核拒绝时，记录拒审原因并通知发布者。该流程将岗位生命周期控制在后端，保证了数据写入的统一性。

### 5.2.3 申请提交与状态更新实现
申请云函数首先验证目标职位是否可申请，再校验是否存在重复申请。通过后，系统创建申请记录，并同步写入职位快照、简历快照和时间线信息。状态更新云函数则在更新前确认操作者是否为职位发布者，并检查状态流转是否合法。通过这种实现方式，系统保证了申请记录的完整性与状态变化的可控性。

### 5.2.4 职位详情与信息保护实现
职位详情云函数在返回数据前，会根据当前申请状态决定是否保留敏感字段。若申请尚未通过，则删除内推码、联系微信和职位链接；若申请通过，则完整返回对应字段。该实现将信息保护逻辑集中在服务端，减少了前端层面的安全风险。

## 5.3 关键实现策略

1. **身份安全策略**：所有关键操作均通过云函数并基于 OPENID 识别身份；
2. **写入安全策略**：职位发布等写操作使用白名单对象构建，避免非预期字段入库；
3. **流程控制策略**：申请状态采用显式状态机，避免非法跳转；
4. **数据分页策略**：列表类接口统一控制 pageSize 上限，提升加载稳定性；
5. **模块解耦策略**：页面与云函数按职责拆分，便于独立迭代与部署。

## 5.4 本章小结
本章围绕页面实现与云函数实现说明了系统的落地方式。可以看出，系统并不是简单地把业务页面堆叠在一起，而是通过身份识别、权限控制、状态机和信息门控等机制，将软件工程中的安全性、可维护性与可扩展性要求落实到具体实现中。

# 第6章 系统运行与应用效果

## 6.1 运行环境与部署说明
本系统运行于微信小程序与腾讯云开发生态中。前端开发与调试依托微信开发者工具，后端逻辑由云函数承载，数据由云数据库进行持久化存储。项目在工程实践中采用“前端构建 + 云函数逐个部署”的方式进行交付：前端在项目根目录安装依赖并在开发者工具中执行 npm 构建，云函数按业务目录逐个上传部署并安装依赖。该部署流程虽然相对手动，但可控性强，适合毕业设计阶段的快速迭代与问题定位。

从运行视角看，系统无需额外维护传统服务器和网关组件，降低了部署成本与运维复杂度。与此同时，业务关键逻辑全部集中在云函数层，前端主要负责交互与展示，使得系统在版本更新和权限治理上更易于维护。

## 6.2 典型业务场景验证

### 6.2.1 场景一：学生发起职位申请
学生登录后进入职位列表页，按关键词或筛选条件定位目标岗位，并在职位详情页发起申请。系统在申请前校验资料完整度，防止在关键信息缺失情况下提交申请。提交成功后，申请记录进入 pending 状态并写入时间线，学生可在申请进度页查看状态变化。该场景验证了“岗位浏览 -> 申请提交 -> 进度追踪”的基础链路有效性。

### 6.2.2 场景二：校友处理申请
校友在申请管理页面查看收到的申请记录，并根据候选人信息执行状态更新。系统在服务端校验操作者是否为职位发布者，同时限制状态流转必须符合状态机规则。处理结果同步写入数据库并反馈至学生侧，实现了“发布者处理 -> 状态更新 -> 用户感知”的闭环流程。

### 6.2.3 场景三：教师审核职位
教师进入审核页面后查看 pending 职位，执行通过或拒绝操作。审核通过后职位状态变更为 published，并可被学生端检索；审核拒绝时记录拒审原因并通知发布者。该场景验证了“发布与审核分离”的治理机制，能够有效控制职位信息质量。

### 6.2.4 场景四：申请通过后的信息解锁
当学生申请被处理为 accepted 后，再次访问职位详情时可查看内推码、联系微信和职位链接。若申请状态未通过，则上述字段不会返回。该场景验证了系统在敏感数据保护上的服务端控制能力，确保了信息可见范围与业务状态一致。

## 6.3 应用效果分析

### 6.3.1 业务闭环效果
系统实现了从职位发布、教师审核、学生申请到校友处理的完整流程，角色协作关系清晰，业务状态可追踪。与仅具备信息发布能力的平台相比，本系统在流程规范性和结果反馈及时性方面表现更优。

### 6.3.2 工程实现效果
系统通过 OPENID 鉴权、角色校验、白名单写入和状态机约束，形成了较完整的后端规则体系。关键业务逻辑集中在云函数层，降低了前端被篡改导致的风险，也提升了代码维护效率。

### 6.3.3 可扩展效果
当前架构对后续功能扩展具有良好兼容性。例如，教师统计页可继续引入更细粒度图表分析，身份认证流程可在现有角色体系上增强，推荐能力也可基于已有行为日志与申请数据逐步演进。

## 6.4 本章小结
本章通过运行环境说明和典型场景验证，证明了系统在真实业务链路中的可用性与可落地性。整体结果表明，该系统不仅能够完成校园内推的核心功能，还在权限治理、状态管理和信息安全方面体现出明确的软件工程价值。

# 第7章 总结与展望

## 7.1 工作总结
本文围绕高校就业内推场景，完成了“酱菜内推系统”的需求分析、架构设计、详细设计和系统实现工作。系统基于微信小程序与腾讯云开发实现，围绕学生、校友、教师三类角色构建了可运行的协同闭环，覆盖职位发布、教师审核、学生申请、校友处理和结果反馈等关键业务环节。

从工程实践角度看，本文的主要成果体现在以下三个方面：

1. **流程规范化**：通过职位审核机制和申请状态机设计，系统将原本离散的业务动作组织为可追踪流程；
2. **权限服务端化**：通过 OPENID 身份识别和角色校验，将关键权限逻辑统一收敛到云函数层；
3. **信息分级化**：通过敏感字段门控机制，实现“申请结果驱动信息解锁”的业务策略。

这些成果说明，本系统不仅在功能上具备可用性，也在软件工程方法上体现了分层设计、职责解耦与规则集中治理等基本原则。

## 7.2 现有不足
受毕业设计周期和资源条件限制，系统仍存在进一步优化空间。

1. 在可视化层面，教师统计页虽已接入真实数据，但展示形式仍可进一步图表化与交互化；
2. 在身份治理层面，当前角色设置以业务流程可用为主，尚可引入更严格的认证机制；
3. 在体验层面，部分辅助功能仍处于基础实现阶段，例如更完善的分享能力和扩展页面；
4. 在工程运维层面，系统已具备基础部署能力，但可观测性和自动化程度仍有提升空间。

这些不足并不影响系统主流程的完整性，但为后续迭代提供了明确方向。

## 7.3 后续展望
基于当前系统基础，后续可沿以下方向持续演进：

1. **增强数据分析能力**：在教师统计模块中引入更丰富的图表组件与多维指标分析；
2. **完善身份认证机制**：结合院校实际流程优化角色认证与审核策略，提高平台可信度；
3. **提升智能匹配能力**：结合申请记录与行为数据，探索职位与学生画像匹配优化方案；
4. **强化运维与治理能力**：逐步完善日志、告警和自动化部署流程，提升系统稳定性。

总体而言，本文在本科毕业设计周期内完成了一个可运行、可验证、可扩展的工程原型，并形成了较完整的需求-设计-实现链路。该成果可为校园内推数字化建设提供实践参考，也为后续研究和产品化扩展奠定了基础。

# 表：角色功能矩阵

| 角色 | 核心功能 | 输入 | 输出 | 约束 |
|---|---|---|---|---|
| 学生 | 浏览职位 | 搜索词、筛选条件 | 职位列表 | 仅显示 published 职位 |
| 学生 | 申请职位 | jobId、个人资料 | 申请记录 | 防重复申请、资料完整度校验 |
| 学生 | 查看进度 | 状态筛选 | 申请进度列表 | 按 userId 查询 |
| 校友 | 发布职位 | 职位表单 | 待审核职位 | 仅 alumni/teacher 可发布 |
| 校友 | 处理申请 | applicationId、目标状态 | 状态更新结果 | 需满足状态机规则 |
| 教师 | 审核职位 | jobId、approve/reject | 审核结果 | 仅 teacher 可审核 |
| 教师 | 查看统计 | 时间范围 | 聚合统计数据 | 仅 teacher/admin 可访问 |

# 表：非功能需求分析

| 类别 | 需求描述 | 设计策略 |
|---|---|---|
| 安全性 | 防止越权访问与敏感信息泄露 | OPENID 鉴权 + 服务端角色校验 + 敏感字段门控 |
| 性能 | 列表查询响应可控 | 统一分页、限制 pageSize 上限 |
| 可维护性 | 便于迭代与问题定位 | 云函数按业务拆分、一函数一职责 |
| 可扩展性 | 支持后续功能增强 | 模块化页面结构 + 结构化数据模型 |
| 可用性 | 低学习成本、流程连贯 | 小程序轻交互 + 状态驱动页面展示 |

# 表：核心云函数职责说明

| 云函数 | 主要职责 | 关键校验 | 关键输出 |
|---|---|---|---|
| login | 用户登录与自动注册 | OPENID 获取 | 用户基础信息 |
| setUserRole | 首次角色设置 | 合法角色枚举 | userType |
| postJob | 发布职位 | 角色校验、必填校验 | 待审核职位ID |
| auditJob | 教师审核职位 | 教师角色、状态校验 | 发布/拒绝结果 |
| getJobList | 获取职位列表 | 分页与筛选参数 | 列表、total、hasMore |
| getJobDetail | 获取职位详情 | jobId 校验、敏感字段门控 | 职位详情 |
| applyJob | 提交申请 | 职位状态、防重复 | 申请成功结果 |
| updateApplicationStatus | 更新申请状态 | 发布者权限、状态机 | 状态更新结果 |
| getApplications | 查询申请列表 | 视角参数 asPublisher | 列表、分页信息 |
| getTeacherStats | 教师统计聚合 | 角色校验 | overview、trend 等 |

# 表：数据库集合与关键字段

| 集合 | 业务含义 | 关键字段 | 说明 |
|---|---|---|---|
| users | 用户信息 | _openid, userType, nickName, profile | 角色与个人资料中心 |
| jobs | 职位信息 | title, salary, location, status, publisherId | 状态驱动职位生命周期 |
| applications | 申请记录 | jobId, userId, status, resumeSnapshot, timeline | 申请流转与历史固化 |
| notifications | 通知信息 | userId, type, title, isRead | 审核与流程消息触达 |
| favorites | 收藏关系 | userId, jobId | 学生收藏职位 |
| userActions | 行为日志 | userId, jobId, actionType, weight | 行为埋点与后续分析 |
