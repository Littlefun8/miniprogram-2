# 第4章 系统详细设计
## 4.1 职位管理模块详细设计
职位模块是整个系统的业务入口，其详细设计围绕发布、审核、查询和详情四类操作展开。
### 4.1.1 职位发布设计
校友在前端提交职位表单后，云函数负责接收这些信息。系统采用**白名单方式**处理，即仅保留与业务相关的字段（如标题、薪资、地点、描述、要求、标签和内推说明等），确保前端无法通过额外字段修改数据库结构。
职位发布流程如下：
1. 校友填写职位信息并提交表单
2. 云函数验证调用者身份与权限
3. 系统提取白名单字段组装职位对象
4. 职位状态初始化为 `pending`，表示待教师审核
5. 职位记录写入数据库，发起教师审核通知流程
该设计的好处是避免了前端在不知情下向数据库注入非预期字段，提高了数据安全性与结构一致性。
### 4.1.2 职位审核设计
教师审核模块负责处理所有处于待审核状态的职位。审核是一个二选一的决策过程：
**审核通过**：
- 职位状态更新为 `published`，表示已发布
- 记录审核教师信息（教师OPENID、审核时间）
- 学生端即刻可检索并浏览该职位
- 向发布校友发送审核通过通知
**审核不通过**：
- 职位状态更新为 `rejected`，表示已驳回
- 保留拒审原因说明
- 校友收到拒审反馈，可选择修改后重新发布
- 学生端无法看到该职位
该流程确保岗位进入学生视野之前都经过了教师背书，从机制上提升了岗位可信度。同时，拒审原因的记录为校友后续优化职位发布提供了反馈。
### 4.1.3 职位查询与详情设计
职位查询在学生和校友两端有不同的需求：
**学生端职位列表**：
- 仅返回状态为 `published` 的职位
- 支持按城市、岗位类型、薪资等维度筛选
- 支持关键词搜索（岗位名、公司名等）
- 采用分页返回，每页数量限制以保证加载速度
**职位详情查询**：
- 基础信息展示给所有已登录用户
- **敏感字段**（内推码、联系微信、职位链接）需要条件解锁
- 解锁条件：当前用户已对该职位申请且申请被接收
- 如果条件不满足，服务端在返回前删除这些字段
这种设计将"信息解锁"与"申请结果"紧密关联，使用户必须通过正常申请流程才能获取内推联系方式，避免了信息被随意传播。
### 4.1.4 设计一致性要求
为保证职位模块在不同页面中呈现一致的业务语义，本系统在设计阶段明确了三项一致性要求：

1. **审核前后语义一致**：职位在学生端是否可见，始终以教师审核结果为准；
2. **角色责任一致**：校友负责发布与处理，教师负责审核，学生负责浏览与申请；
3. **信息展示一致**：列表页展示概览信息，详情页展示完整业务信息，并按申请结果分级展示敏感内容。

该约束避免了“同一职位在不同页面表现不一致”的问题，为后续实现和测试提供统一参照。
## 4.2 申请与流转模块详细设计
### 4.2.1 申请提交设计
申请模块的设计目标是保证申请过程可追踪、可控制且不可重复。学生申请时，系统首先校验目标职位是否处于可申请状态，然后检查是否已经提交过该职位申请，若已存在则直接拒绝重复申请。通过该方式，系统避免同一用户对同一职位重复投递，减少数据冗余与后续处理成本。
申请记录中保存了申请人信息、职位快照、简历快照、时间线等数据。其中，**简历快照**用于保存申请当时的学生简历信息，保证历史记录不会因后续申请者修改简历而失真；**职位快照**保存岗位信息，防止职位被校友修改后导致申请记录语义不清。
### 4.2.2 申请处理阶段设计
申请处理在业务上分为三个阶段：

1. **提交阶段**：学生提交申请后进入待处理队列；
2. **处理阶段**：校友查看申请材料并进行沟通、筛选；
3. **结果阶段**：校友给出接收或拒绝结果，学生据此查看后续信息。

该分阶段设计的核心目标是让学生能感知流程进展，让校友能稳定处理申请，同时让教师在统计与监管页面看到清晰的过程数据。

在实现层面，系统会对申请过程做合法性校验，防止重复处理和越权操作；本章不展开技术校验细节，具体实现见第5章。
### 4.2.3 敏感信息解锁与保护机制
职位详情中存在三类**敏感字段**，需要特殊保护：
- `referralCode`：内推码（校友与招聘方的内部推荐凭据）
- `contactWechat`：校友的微信联系方式
- `jobLink`：职位链接
**保护策略**：
| 申请状态 | 敏感字段返回 | 说明 |
|---------|----------|------|
| 未申请 / 申请中 / 已拒绝 | 不返回 | 敏感信息对这些状态的用户不可见 |
| 已接受 | 返回 | 只有申请被接受的用户才能看到内推信息 |
这种**服务端门控**策略将"信息解锁"与"申请结果"紧密关联，确保学生必须通过正常申请流程才能获取内推信息。
## 4.3 模块协作与流程完整性
从"申请→处理→解锁"的端到端流程看，系统涉及多个模块与接口的协作：
1. 学生发起申请 → `applyJob` 云函数创建申请记录
2. 校友查看申请 → `getApplications` 云函数返回待处理申请列表
3. 校友处理申请 → `updateApplicationStatus` 推进申请状态
4. 学生查看详情 → `getJobDetail` 根据申请状态返回不同内容
该流程设计确保了整个系统的业务逻辑自洽且难以被绕过。
## 4.4 本章小结
本章深化了系统的三个核心模块设计：职位发布审核模块聚焦于"多角色协作的生命周期管理"，申请流转模块聚焦于"严格的状态约束与历史准确性"，敏感信息保护聚焦于"权益与流程的强绑定"。这些设计决策使系统的业务规则更清晰、可执行且可验证，为后续的实现工作提供了明确的约束基线。
