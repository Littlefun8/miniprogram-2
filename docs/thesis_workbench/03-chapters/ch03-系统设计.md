# 第3章 系统设计

## 3.1 系统架构设计

### 3.1.1 架构目标
系统架构设计围绕高校内推业务的运行需求展开，目标如下：

（1）在微信小程序场景下建立稳定、清晰的分层结构，保证页面调用与服务处理关系明确；

（2）保证身份识别、角色判定与业务处理在服务端完成，避免客户端越权访问；

（3）保证职位发布、职位审核、申请处理、通知反馈等核心流程在同一架构下可持续扩展；


### 3.1.2 系统架构
系统由微信小程序端、云函数服务端和云数据库三部分组成。小程序端负责页面交互与结果展示，云函数负责业务处理与权限校验，云数据库负责数据存储与查询。本系统不包含独立 Web 端，不采用微服务网关模式。

系统运行时，小程序页面通过 `wx.cloud.callFunction` 调用云函数，云函数在服务端完成身份判定、角色校验和业务处理，再读写数据库并将结果返回页面。该架构与项目当前实现保持一致。

为突出权限边界与角色分工，图3-1在三层技术架构之外增加“对象层（角色权限视角）”作为表达辅助，用于说明学生、校友、教师/管理员在同一业务链路中的权限差异。

从分层职责看：

（1）表现层包括职位列表、职位详情、申请管理、通知、教师统计等页面；

（2）业务层包括 `login`、`setUserRole`、`postJob`、`auditJob`、`applyJob`、`updateApplicationStatus`、`getNotifications`、`getTeacherStats` 等云函数；

（3）数据层包含用户、职位、申请、通知等业务数据集合。

## 3.2 功能模块设计

本节说明系统功能在工程实现中的模块组织方式。系统围绕表现层、逻辑层和数据层展开，每个模块都从页面交互、服务处理和数据存储三个方面进行设计说明。

图3-2 系统功能组件图

### 3.2.1 用户与权限管理模块设计

该模块由微信授权入口、角色路由控制和本地状态管理三部分组成。**表现层**负责管理登录授权提示、静默登录状态维持和角色页面分流；**逻辑层**通过独立的登录鉴权接口与角色写入服务完成身份识别；**数据层**负责持久化保存用户角色与基础资料。

在该模块的设计中，客户端负责登录状态的轻量级维护，而核心权限判断严格依赖服务端。客户端本地缓存仅用于减少频繁的重复登录请求，用户的最终角色权限和身份标识仍以服务端的实时校验结果为准，以此阻断越权访问。此部分的逻辑层服务主要由 `login` 云函数与 `setUserRole` 云函数提供支撑。

### 3.2.2 职位管理模块设计

该模块由职位动态表单组件、审核处理服务、列表分页查询和详情字段门控组成。**表现层**负责数据收集与列表视图渲染；**逻辑层**负责职位发布写入、状态审核流转和详情数据组装；**数据层**维护职位生命周期状态和展示字段。

在系统设计中，职位数据具有明确的状态机特性。职位发布后默认进入待审核状态，审核结果作为数据网关，决定其是否能进入前台展示列表。此外，当职位详情涉及联系方式、内推码等敏感字段时，系统采用服务端数据脱敏策略，由逻辑层执行鉴权门控后再返回页面，以防隐私泄露。该模块的核心业务流转由 `postJob`、`auditJob`、`getJobList` 及 `getJobDetail` 等云函数协同完成。

### 3.2.3 申请与进度管理模块设计

该模块由申请提交入口、防重复校验逻辑、状态流转处理和进度查询组件组成。**表现层**负责投递交互与进度时间线展示；**逻辑层**负责并发查重、状态树更新和业务记录维护；**数据层**保存申请快照记录与时间线流转信息。

为保证核心业务数据的一致性，系统在设计申请投递流程时，强制要求数据写入前必须经过服务端的防重复申请校验；申请状态的更新严格遵循既定状态机规则；进度查询则基于当前用户的身份标识（OPENID）进行权限过滤。上述并发控制与状态流转逻辑依托于 `applyJob`、`updateApplicationStatus` 与 `getApplications` 云函数实现。

### 3.2.4 通知与统计模块设计

该模块由通知读取组件、统计查询接口和聚合结果展示组成。通知数据由各相关业务节点（如审核、处理申请）在流转时触发写入，**表现层**按用户身份定向拉取并渲染；统计页面由具备管理员权限的教师端定向访问。

在系统设计中，通知模块承担系统级业务反馈，统计模块支撑宏观运行观察。为有效降低客户端性能开销并保障数据安全，复杂的统计运算与数据聚合均交由服务端完成，表现层仅接收格式化后的结果数据进行图表渲染，避免在客户端暴露全量业务数据。其通知拉取与统计聚合功能分别由 `getNotifications` 与 `getTeacherStats` 云函数封装实现。


## 3.3 交互设计
本节用时序图说明页面、云函数、数据库之间的调用顺序。时序图用于表达“请求发起、业务处理、数据读写、结果返回”的全过程。

### 3.3.1 用户与权限管理交互设计
该模块交互围绕“登录与角色确认”“登录态持久化与免登录识别”两个场景展开。

图3-3 登录与角色确认时序图

登录与角色确认场景主要涉及微信客户端、`login` 云函数、`setUserRole` 云函数和用户数据集合。用户进入系统后，客户端先发起登录请求，服务端根据 OPENID 查询用户信息并返回当前角色状态。

当返回结果中未包含角色信息时，普通用户仅可在学生/校友范围内完成首次角色选择，并携带 `userType` 参数调用 `setUserRole` 写入角色字段；教师（管理员）角色由后台管理或管理员审核流程预置或写入，不通过普通前端自助选择。若登录请求异常或角色写入失败，系统触发异常处理逻辑并提示用户，同时保留重新触发入口。

图3-4 登录状态持久化与免登录识别时序图

登录态持久化场景主要涉及本地缓存、`login` 云函数与页面路由。小程序重新打开时，客户端优先读取 `isLoggedIn`、`userType`、`userInfo`，并发起服务端校验请求。

若服务端校验通过，系统恢复登录状态并进入目标页面；若本地状态缺失或校验失败，系统清理无效状态并引导用户重新登录，从而避免错误身份继续访问。

### 3.3.2 职位管理交互设计
该模块交互围绕“职位发布”“审核流转”“列表与详情返回”三个场景展开。

图3-5 职位发布时序图

职位发布场景主要涉及校友端页面、`postJob` 云函数和职位数据集合。客户端提交表单时携带职位基础字段，云函数先进行参数与角色合法性校验。

校验通过后，服务端写入职位记录并将 `status` 置为 `pending`；校验不通过时直接返回错误信息，客户端触发异常处理逻辑并提示用户补全字段或调整提交内容。

图3-6 职位审核流转时序图

职位审核场景主要涉及教师端页面、`auditJob` 云函数、职位集合与通知集合。教师提交审核动作后，服务端先校验教师身份和职位当前状态。

当条件满足时，系统按审核动作更新职位状态，并向发布者写入审核通知；当角色不符、状态不符或缺少驳回原因时，服务端终止更新并返回对应错误分支。

图3-7 职位列表与详情返回时序图

职位查询场景主要涉及列表页面、详情页面、`getJobList` 云函数和 `getJobDetail` 云函数。客户端先按分页参数请求职位列表，再按 `jobId` 请求职位详情。

详情返回前，服务端根据当前用户申请状态判断敏感字段是否可见。若用户申请状态不是 `accepted`，则移除联系方式、内推码、链接等字段后再返回，确保展示范围符合业务规则。

### 3.3.3 申请与进度管理交互设计
该模块交互围绕“申请提交”“申请处理”“进度查询”三个场景展开。

图3-8 申请提交时序图

申请提交场景主要涉及学生端页面、`applyJob` 云函数、职位集合与申请集合。客户端提交请求时携带 `jobId` 及可选背书信息，服务端先校验职位是否存在且处于可申请状态。

校验通过后，服务端继续执行重复申请检查（`jobId + userId` 联合条件）。若存在重复记录则返回拦截结果；若不存在则写入申请记录、简历快照、职位快照和初始时间线，并返回提交成功状态。

图3-9 申请处理时序图

申请处理场景主要涉及校友端页面、`updateApplicationStatus` 云函数、申请集合与职位集合。校友提交处理动作时携带 `applicationId` 和目标状态，服务端先校验参数完整性与目标状态合法性。

随后服务端验证调用者是否为职位发布者，并按状态机规则检查流转是否允许（`pending -> processing -> accepted/rejected`）。校验通过后写入新状态和处理信息；校验失败则返回无权限或非法流转分支。

图3-10 申请进度查询时序图

进度查询场景主要涉及学生/校友页面、`getApplications` 云函数与申请集合。客户端按角色传递查询视角参数（本人申请或发布者视角），并携带分页与状态筛选条件。

服务端按 OPENID 构造查询条件后返回对应申请列表、总数和分页标识，页面据此渲染状态和时间线，形成可追踪的处理过程视图。

### 3.3.4 通知与统计交互设计
该模块交互围绕“通知生成与查看”“统计查询与返回”两个场景展开。

图3-11 通知生成与查看时序图

通知场景主要涉及业务云函数、通知集合、通知页面和 `getNotifications` 云函数。审核或申请处理完成后，相关业务函数向通知集合写入结果消息。

用户进入通知页面时，客户端携带分页参数发起查询请求，服务端按 OPENID 返回通知列表、总数和未读数；若查询异常，系统触发异常处理逻辑并提示用户重试。

图3-12 统计查询与返回时序图

统计场景主要涉及教师统计页面、`getTeacherStats` 云函数及相关业务数据集合。客户端携带时间范围参数发起统计请求，服务端先校验调用角色是否为教师或管理员。

身份通过后，服务端执行聚合计算并返回总览数据、状态分布与趋势结果；身份不通过时返回权限拒绝分支，页面按返回结果进行提示。

## 3.4 数据库设计
本节在前述模块与交互设计基础上，给出数据库的概念结构、逻辑结构与核心数据表设计。数据库设计目标是保证角色权限、状态流转、防重复申请和通知反馈等关键业务具备可追踪、可约束、可扩展的数据支撑。

### 3.4.1 概念结构设计
概念结构设计的核心目的，是先从业务语义出发定义“系统需要管理哪些对象”，再明确对象之间的联系，为后续逻辑结构与字段落表提供统一依据。结合本系统实际流程，可抽象出七类实体：用户、公司、职位、申请、通知、收藏关系、行为记录。

（1）用户实体（Users）：用于描述账号身份与权限边界。其属性可分为三类：身份标识属性（如 `_openid`、`userType`）、展示属性（如 `nickName`、`avatarUrl`）、扩展资料属性（如 `profile`、`isVerified`、`createTime`、`updateTime`）。本实体属性图如图3-13所示。

图3-13 用户实体属性图

图3-14 职位实体属性图

图3-15 申请实体属性图

（4）通知实体（Notifications）：用于描述审核反馈与流程通知。其属性可分为接收对象属性（如 `userId`）、消息属性（如 `type`、`title`、`content`、`relatedId`）、状态属性（如 `isRead`）、时间属性（如 `createTime`）。本实体属性图如图3-16所示。

图3-16 通知实体属性图

（5）公司实体（Companies）：用于描述职位所属组织信息。其属性包括公司名称、行业、规模、地点、简介和创建时间等，用于补充职位展示与统计维度。

（6）收藏关系实体（Favorites）：用于描述用户与职位的收藏关系。其属性包括用户标识、职位标识和收藏时间，用于实现“用户-职位”多对多关系管理。

（7）行为记录实体（UserActions）：用于描述用户在职位上的行为轨迹。其属性包括行为类型、停留时长、行为权重和记录时间，用于后续推荐分析与统计扩展。

通过实体联系分析，可得到以下核心关系：

（1）用户发布职位（1对多）：一个校友用户可发布多个职位；

（2）用户提交申请（1对多）：一个学生用户可提交多个申请；

（3）职位包含申请（1对多）：一个职位可对应多个申请记录；

（4）用户接收通知（1对多）：一个用户可接收多条业务通知；

（5）公司关联职位（1对多）：一家公司可对应多个职位；

（6）用户收藏职位（多对多，经 Favorites 关系实体实现）；

（7）用户触发职位行为（1对多，经 UserActions 关系实体记录）。

### 3.4.2 逻辑结构设计
逻辑结构设计的目的，是将概念层的实体关系转化为可实现的集合结构与字段约束，确保系统在查询效率、数据一致性和后续扩展方面具备工程可行性。本系统采用微信云开发集合模型，逻辑映射原则如下：

（1）每个核心实体映射为一个核心集合，实体主标识由 `_id` 或 `_openid` 承担；

（2）实体间联系通过关联字段（如 `publisherId`、`jobId`、`userId`）建立；

（3）流程型业务统一采用状态字段（如 `status`）和时间字段（如 `createTime`、`updateTime`）支持审计与追踪；

（4）高频查询路径通过组合索引保障性能，并通过唯一约束保障关键业务规则。

据此，核心关系模式可表示为：

（1）Users（`_id`, `_openid`, `nickName`, `avatarUrl`, `userType`, `isVerified`, `profile`, `createTime`, `updateTime`）；

（2）Companies（`_id`, `name`, `description`, `industry`, `size`, `location`, `createTime`）；

（3）Jobs（`_id`, `title`, `salary`, `company`, `location`, `tags`, `status`, `publisherId`, `recommenderComment`, `jobLink`, `applicationCount`, `createTime`, `updateTime`）；

（4）Applications（`_id`, `jobId`, `userId`, `publisherId`, `status`, `timeline`, `resumeSnapshot`, `createTime`, `updateTime`）；

（5）Notifications（`_id`, `userId`, `type`, `relatedId`, `isRead`, `title`, `content`, `createTime`）；

（6）Favorites（`_id`, `userId`, `jobId`, `createTime`）；

（7）UserActions（`_id`, `userId`, `jobId`, `actionType`, `stayDuration`, `weight`, `createTime`）。

其中，`Jobs.publisherId`、`Applications.userId`、`Applications.publisherId`、`Notifications.userId`、`Favorites.userId`、`UserActions.userId` 均通过 OPENID 体系完成身份关联。逻辑层关键约束包括：申请防重复约束（`jobId + userId` 唯一）、收藏防重复约束（`userId + jobId` 唯一）、用户视角状态查询索引（`userId + status`）以及发布者视角状态查询索引（`publisherId + status`）。
