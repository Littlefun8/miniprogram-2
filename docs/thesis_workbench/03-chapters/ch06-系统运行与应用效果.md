# 第6章 系统运行与应用效果

## 6.1 运行环境与部署说明
本系统运行于微信小程序与腾讯云开发生态中。前端开发与调试依托微信开发者工具，后端逻辑由云函数承载，数据由云数据库进行持久化存储。项目在工程实践中采用“前端构建 + 云函数逐个部署”的方式进行交付：前端在项目根目录安装依赖并在开发者工具中执行 npm 构建，云函数按业务目录逐个上传部署并安装依赖。该部署流程虽然相对手动，但可控性强，适合毕业设计阶段的快速迭代与问题定位。

从运行视角看，系统无需额外维护传统服务器和网关组件，降低了部署成本与运维复杂度。与此同时，业务关键逻辑全部集中在云函数层，前端主要负责交互与展示，使得系统在版本更新和权限治理上更易于维护。

## 6.2 典型业务场景验证

### 6.2.1 场景一：学生发起职位申请
学生登录后进入职位列表页，按关键词或筛选条件定位目标岗位，并在职位详情页发起申请。系统在申请前校验资料完整度，防止在关键信息缺失情况下提交申请。提交成功后，申请记录进入 pending 状态并写入时间线，学生可在申请进度页查看状态变化。该场景验证了“岗位浏览 -> 申请提交 -> 进度追踪”的基础链路有效性。

### 6.2.2 场景二：校友处理申请
校友在申请管理页面查看收到的申请记录，并根据候选人信息执行状态更新。系统在服务端校验操作者是否为职位发布者，同时限制状态流转必须符合状态机规则。处理结果同步写入数据库并反馈至学生侧，实现了“发布者处理 -> 状态更新 -> 用户感知”的闭环流程。

### 6.2.3 场景三：教师审核职位
教师进入审核页面后查看 pending 职位，执行通过或拒绝操作。审核通过后职位状态变更为 published，并可被学生端检索；审核拒绝时记录拒审原因并通知发布者。该场景验证了“发布与审核分离”的治理机制，能够有效控制职位信息质量。

### 6.2.4 场景四：申请通过后的信息解锁
当学生申请被处理为 accepted 后，再次访问职位详情时可查看内推码、联系微信和职位链接。若申请状态未通过，则上述字段不会返回。该场景验证了系统在敏感数据保护上的服务端控制能力，确保了信息可见范围与业务状态一致。

## 6.3 应用效果分析

### 6.3.1 业务闭环效果
系统实现了从职位发布、教师审核、学生申请到校友处理的完整流程，角色协作关系清晰，业务状态可追踪。与仅具备信息发布能力的平台相比，本系统在流程规范性和结果反馈及时性方面表现更优。

### 6.3.2 工程实现效果
系统通过 OPENID 鉴权、角色校验、白名单写入和状态机约束，形成了较完整的后端规则体系。关键业务逻辑集中在云函数层，降低了前端被篡改导致的风险，也提升了代码维护效率。

### 6.3.3 可扩展效果
当前架构对后续功能扩展具有良好兼容性。例如，教师统计页可继续引入更细粒度图表分析，身份认证流程可在现有角色体系上增强，推荐能力也可基于已有行为日志与申请数据逐步演进。

## 6.4 本章小结
本章通过运行环境说明和典型场景验证，证明了系统在真实业务链路中的可用性与可落地性。整体结果表明，该系统不仅能够完成校园内推的核心功能，还在权限治理、状态管理和信息安全方面体现出明确的软件工程价值。
