# 第4章 系统实现

## 4.1 实现说明
本章按照第3章的模块顺序，给出系统的具体实现过程。实现层面采用“页面入口 + 云函数处理 + 数据持久化 + 结果返回”的描述方式，对关键校验逻辑、状态流转和异常分支进行说明。

当前版本以前后端分离的微信云开发模式为主：客户端页面负责交互与渲染，云函数负责业务校验与写入，云数据库负责数据持久化。各模块实现与第3章设计保持一一对应关系。

## 4.2 用户与权限管理模块实现
该模块由登录鉴权、角色写入和本地会话恢复三部分组成，核心云函数为 `login` 和 `setUserRole`。

（1）客户端启动时先读取本地状态（`isLoggedIn`、`userType`、`userInfo`），并调用 `login` 执行静默校验。实现如图4-1所示。

图4-1 应用启动与静默登录界面。建议截图内容包括：小程序启动后自动进入首页或个人中心的状态恢复结果，界面上能够看到登录状态、昵称、头像或角色标签等信息。该图主要用于说明系统在启动时通过 `login` 完成静默校验并恢复本地会话，截图中无需展示任何敏感标识。

（2）`login` 通过 OPENID 查询 `users` 集合，若用户不存在则自动注册初始档案，若存在则返回完整用户信息。该过程可与图4-1中的登录态恢复结果对应。

（3）当用户尚未设置角色时，客户端触发角色确认流程：普通用户仅在学生/校友范围内完成首次角色写入；教师（管理员）账号由管理端预置或人工审核后写入。实现如图4-2所示。

图4-2 角色确认与首次写入界面。建议截图内容包括：学生/校友角色确认弹窗或页面，以及首次写入成功后的提示结果；教师（管理员）角色建议通过管理端配置页面或权限说明图展示其非前端自助选择路径。截图时应保留角色确认按钮、提示信息和成功反馈区域，突出 `setUserRole` 仅允许首次写入的约束。

（4）`setUserRole` 限制角色只能首次写入，已设置角色时返回冲突结果，避免客户端重复改角色；教师（管理员）权限仍以服务端账号校验结果为准，不以前端提交参数为准。该限制结果可与图4-2中的首次写入流程对应。

## 4.3 职位管理模块实现
该模块覆盖职位发布、职位审核、职位列表和职位详情四个实现环节，主要云函数为 `postJob`、`auditJob`、`getJobList`、`getJobDetail`。

（1）发布实现：校友在发布页面提交职位信息，`postJob` 校验必填字段（`title/salary/company/location`）及调用者角色，仅允许校友或教师发布；校验通过后写入 `jobs` 集合，并将状态初始化为 `pending`。页面实现如图4-4所示。

图4-4 职位发布页面。建议截图内容包括：职位名称、薪资范围、公司名称、工作地点、标签、岗位链接、发布人姓名等表单项，以及校验失败时的提示信息。截图时应保留表单主体区域，便于展示 `postJob` 对必填字段的校验过程。

（2）审核实现：教师在审核页面提交通过/拒绝动作，`auditJob` 校验教师身份、职位当前状态和驳回原因（拒绝时必填），随后更新职位状态并向发布者写入审核通知。实现如图4-5所示。

图4-5 职位审核页面。建议截图内容包括：待审核职位列表、职位卡片、通过按钮、拒绝按钮以及拒绝原因输入框。截图应突出审核操作入口，并保留审核结果提示区域，以说明 `auditJob` 的身份校验和状态更新逻辑。

（3）列表实现：`getJobList` 按分页参数与筛选条件返回职位列表，默认只返回 `published` 职位。页面实现如图4-6所示。

图4-6 职位列表页面。建议截图内容包括：搜索框、筛选条件、职位卡片、分页加载或“没有更多数据”提示。截图时保留列表区域和筛选区域，便于体现 `getJobList` 的分页与过滤效果。

（4）详情实现：`getJobDetail` 在返回详情前查询当前用户申请状态，若状态不是 `accepted`，则移除 `referralCode/contactWechat/jobLink` 等敏感字段后再返回。页面实现如图4-7所示。

图4-7 职位详情与敏感字段门控页面。建议截图内容包括：职位基础信息、申请按钮、职位说明以及未通过申请时被隐藏的内推码、联系方式和岗位链接区域。若需要体现关键分支，可同时保留“已申请/未申请”状态下的字段差异，并对敏感信息进行打码。

该模块实现后，职位从发布、审核到展示形成闭环。模块实现如图4-4至图4-7所示。


## 4.4 申请与进度管理模块实现
该模块覆盖申请提交、申请处理与进度查询，重点体现在防重复提交与状态机流转。

（1）申请提交实现：学生在职位详情页点击申请后调用 `applyJob`，服务端依次执行职位可申请校验、重复申请校验（`jobId + userId`）和申请写入。实现如图4-8所示。

图4-8 申请确认与重复申请提示页面。建议截图内容包括：职位详情页中的“申请职位”按钮、申请确认弹窗，以及重复申请时的拦截提示或按钮置灰效果。该图主要用于说明 `applyJob` 在提交前的可申请校验和重复申请校验。

（2）`applyJob` 写入内容包括基础申请信息、职位快照、可选简历快照和初始时间线，同时同步递增职位申请数；

（3）申请处理实现：校友在管理页调用 `updateApplicationStatus`，服务端先校验调用者是否为职位发布者，再校验目标状态是否合法。页面实现如图4-9所示。

图4-9 学生申请进度页面。建议截图内容包括：学生视角下的申请列表、状态标签、时间线、申请结果与职位跳转入口。截图时应保留状态变化区域，以展示 `getApplications` 在学生视角下返回的进度结果。

（4）状态流转实现：`updateApplicationStatus` 严格按 `pending -> processing -> accepted/rejected` 执行，不允许跨阶段更新。实现如图4-10所示。

图4-10 校友申请管理页面。建议截图内容包括：校友视角的申请列表、待处理/处理中/已通过/已拒绝标签，以及开始处理、通过和拒绝等操作按钮。该图用于展示 `getApplications` 在发布者视角下返回的申请记录。

（5）进度查询实现：`getApplications` 根据 `asPublisher` 参数切换学生视角或发布者视角，按分页返回申请记录与状态结果。状态更新结果可与图4-11对应。

## 4.5 通知与统计模块实现
该模块包含通知查询与教师统计两类支撑能力，核心云函数为 `getNotifications` 和 `getTeacherStats`。

（1）通知查询实现：`getNotifications` 按 OPENID 查询当前用户通知列表，支持分页、未读数统计与排序返回。页面实现如图4-12所示。

图4-12 通知列表与未读状态页面。建议截图内容包括：通知列表、未读数量、通知类型、读取状态以及点击通知后的跳转入口。截图时应保留列表首屏和未读标识区域，以说明 `getNotifications` 的排序与未读统计效果。

（2）通知写入来源：当前版本的通知主要由职位审核环节（`auditJob`）写入，通知页面负责读取与展示；

（3）统计实现：教师端调用 `getTeacherStats`，服务端先校验角色（`teacher/admin`），再聚合 `users`、`jobs`、`applications` 等数据，返回总览、分布、热门岗位、趋势和漏斗结果。页面上半部分如图4-13所示。

（4）前端渲染实现：统计页面只接收聚合结果并进行图表渲染，复杂计算均在服务端完成。页面下半部分如图4-14所示。

## 4.6 部署与联调实现
系统部署采用小程序构建与云函数逐项部署方式，避免批量部署导致的失败定位困难。联调顺序如下：

（1）登录与角色设置；

（2）职位发布与审核；

（3）职位列表与详情查询；

（4）申请提交、申请处理与进度查询；

（5）通知与统计查询。

联调过程中重点校验角色权限、状态流转和分页返回三个维度，确保核心流程在多角色场景下可连续运行。
