# 第6章 关键技术与优化

## 6.1 身份认证与权限控制

### 6.1.1 基于OPENID的身份识别机制
本系统采用微信云开发提供的 `cloud.getWXContext().OPENID` 作为用户身份的唯一可信来源。这种方式相比于直接依赖前端传参，具有本质的安全优势：

**安全优势**：
- OPENID由微信服务器签发，前端无法伪造或篡改
- 每次云函数调用时，云开发平台自动验证OPENID的真实性
- 即使网络被中间人攻击，也无法伪造身份

**实现流程**：
```javascript
// 云函数端
const { OPENID } = cloud.getWXContext();
// 此时OPENID已由平台验证，可以信任使用
const user = await db.collection('users').doc(OPENID).get();
```

### 6.1.2 角色校验与权限控制
系统在身份识别基础上，进一步实施**角色级权限控制**。

**校验流程**：
1. 获取OPENID，查询 `users` 集合中该OPENID的 `userType` 字段
2. 根据操作所需权限，校验用户角色是否满足要求
3. 若权限不足，返回403错误
4. 若权限充足，执行业务操作

**权限矩阵**：
| 操作 | 所需角色 | 错误码 |
|------|---------|-------|
| 发布职位 | alumni / teacher | 403 |
| 审核职位 | teacher | 403 |
| 查看申请 | 职位发布者(owner) | 403 |
| 处理申请 | 职位发布者(owner) | 403 |
| 查看统计 | teacher | 403 |

这种**"身份+角色+资源归属"的三层验证**确保了权限控制的严密性。

## 6.2 应用状态机设计

### 6.2.1 职位生命周期状态机
职位从发布到最终状态的转移遵循严格的有限状态机模型。

**状态转移图**：
```
pending (待审核)
  ├→ published (已发布) [教师审核通过]
  └→ rejected (已驳回) [教师审核拒绝]

published (已发布)
  └→ (持久存在，除非手动下架)

rejected (已驳回)
  └→ (终态)
```

**转移约束**：
- 只有教师可以推进状态
- pending→published 和 pending→rejected 是仅有的允许转移
- published 和 rejected 都是终态，不可逆

**实现约束代码示例**：
```javascript
const legalJobTransitions = {
  'pending': ['published', 'rejected'],
  'published': [],  // 终态
  'rejected': []    // 终态
};

function isLegalJobTransition(fromStatus, toStatus) {
  return legalJobTransitions[fromStatus]?.includes(toStatus);
}
```

### 6.2.2 申请生命周期状态机
申请状态机相比职位更复杂，支持中间状态（processing）。

**状态转移图**：
```
pending (初始申请)
  ├→ processing (校友正在处理)
  │   ├→ accepted (接受申请)
  │   └→ rejected (拒绝申请)
  │
  ├→ accepted (直接接受)
  └→ rejected (直接拒绝)

accepted / rejected (终态)
```

**转移约束**：
- 只有职位发布者可以推进申请状态
- 可以跳过 processing 直接到终态
- accepted 和 rejected 都是终态，一旦到达不可逆转

**约束代码示例**：
```javascript
const legalAppTransitions = {
  'pending': ['processing', 'accepted', 'rejected'],
  'processing': ['accepted', 'rejected'],
  'accepted': [],   // 终态
  'rejected': []    // 终态
};
```

**状态转移的业务意义**：
- `pending → processing`：校友开始审阅申请
- `processing → accepted`：校友接受申请，生成内推码
- `pending → accepted`：校友快速接受（跳过处理阶段）
- `* → rejected`：任何状态都可拒绝，拒绝后不可恢复

这种设计使申请流程既具备过程透明性（通过processing中间态），又支持高效处理（直接跳跃）。

## 6.3 敏感信息分级保护

### 6.3.1 服务端字段门控策略
系统采用**服务端门控**而非前端隐藏，这是安全设计的关键差异：

**前端隐藏的问题**：
```javascript
// 不安全：前端隐藏
const jobDetail = getJobDetailFromServer(); // 包含敏感字段
if (userStatus === 'accepted') {
  displaySensitiveFields(jobDetail);  // 展示敏感字段
} else {
  // 隐藏敏感字段，但数据已在前端内存中
  displayBasicFields(jobDetail);
}
```

**服务端门控的优势**：
```javascript
// 安全：服务端门控
const sensitiveFields = ['referralCode', 'contactWechat', 'jobLink'];
if (userApplicationStatus !== 'accepted') {
  sensitiveFields.forEach(field => delete jobDetail[field]);  // 在服务端删除
}
return jobDetail;  // 返回给前端的数据中不包含敏感字段
```

### 6.3.2 信息解锁条件与业务流程的强绑定
敏感信息的解锁不是简单的权限检查，而是与**申请结果**紧密关联。

**解锁流程**：
1. 学生申请职位 → 申请状态为 `pending`，无法看到内推信息
2. 校友审核申请 → 若接受，申请状态更新为 `accepted`
3. 学生再次查看职位 → `getJobDetail` 检测到 `accepted` 状态，返回内推码

**业务价值**：
- 学生获取内推码的**唯一路径**是通过校友的接受
- 避免了内推信息被预泄露或滥用
- 确保了校友的推荐资源不被浪费

## 6.4 数据库与索引优化

### 6.4.1 核心集合设计
系统核心数据库集合包括：

| 集合名 | 主要字段 | 关键用途 |
|-------|---------|--------|
| `users` | OPENID, userType, createdAt | 用户身份与角色管理 |
| `jobs` | _id, publisherId, status, title, company, createdAt | 职位生命周期 |
| `applications` | _id, userId, jobId, status, userSnapshot, jobSnapshot, createdAt | 申请记录与快照 |
| `notifications` | _id, recipientId, type, read, createdAt | 通知与消息 |

**字段设计原则**：
- 统一采用 camelCase 命名（如 `publisherId` 而非 `publisher_id`）
- 状态字段采用字符串枚举（如 `"pending"` 而非数字 `0`）
- 时间戳采用毫秒精度的Unix时间戳
- 关键外键显式保存（如 `jobId`, `userId`）

### 6.4.2 高频查询索引
系统根据实际查询路径创建索引，提升性能。

**职位列表查询**：
```javascript
// 查询条件
db.collection('jobs')
  .where({ status: 'published' })
  .orderBy('createdAt', 'desc')
  .skip(skip).limit(limit);

// 需要的复合索引
// { status: 1, createdAt: -1 }
```

**申请列表查询**：
```javascript
// 查询条件
db.collection('applications')
  .where({ publisherId: OPENID })
  .orderBy('status')
  .orderBy('createdAt', 'desc');

// 需要的复合索引  
// { publisherId: 1, status: 1, createdAt: -1 }
```

**索引创建**：
`createIndexes` 云函数负责批量创建这些索引，并作为运维入口留存。

## 6.5 错误处理策略

### 6.5.1 分层错误码设计
系统采用标准HTTP错误码，按层级分类。

**错误码映射**：
| 错误码 | 含义 | 例子 |
|-------|------|------|
| 400 | 参数错误 | 缺少必填字段、字段格式不合法 |
| 401 | 未登录或身份无效 | 用户未调用login；会话过期 |
| 403 | 权限不足 | 非校友调用postJob；非教师调用auditJob |
| 404 | 资源不存在 | 职位ID不存在；申请记录不存在 |
| 409 | 业务冲突 | 重复申请；非法状态转移 |
| 500 | 服务器错误 | 数据库操作失败；内部异常 |

### 6.5.2 错误处理的可观测性
每个错误码都对应明确的业务规则，便于：
- **前端差异化处理**：根据错误码执行不同的用户提示与恢复动作
- **测试边界用例**：每个错误码对应一类测试场景
- **日志聚类分析**：按错误码统计问题类型与发生频率

## 6.6 本章小结

本章从身份认证、权限控制、状态机设计、敏感信息保护、数据库索引和错误处理等多个技术维度阐述了系统的设计深度。这些技术选择不是简单的"工程实践"，而是基于**安全性、可维护性、可扩展性**的明确考量。通过这些关键技术的正确应用，系统实现了"能跑"到"能靠"的质量跨越。
